## 范围

**V4**：缺口计量做实 + 致死率参数化。
**V5**：§八.5 流水按周期清零、§八.6 消费残差分派、§八.7 分配残差按权重、§八.8 读数与结算同源。

## 六处必须先想清的决定（前两处是控制器骨架里的真错）

### ① 口粮口径要换载体，不是修字面量

`83` 是 `10,000 ÷ 120` 的**商**。拿它当"每人每日口粮"再乘人口，**残差在定义上就已经丢了**——留着它（哪怕只当底数）就是把陷阱留在原地。
⇒ `EconomyVocabulary` 只留**口径**（每人每 120 天 10,000 毫粮 + 120 天）与**由它推出的两个纯函数**（`cumulativeRationMilli` / `dailyRationMilli`）；
**三处 `DAILY_GRAIN_MILLI_PER_PERSON` 声明全删**（`EconomyVocabulary` / `EconomySettlement` / `EconomySeeder`）。
★ 这与 plan2 定的"既有 `public static final` 一个不删"**有意破例**：那条纪律保护的是"被引用的事实"，而这个是**已被 spec §八.6 判定为错的近似**。
★ 唯一拼写点仍由 `EconomyVocabularyGuardTest` 把守（它的 token 要跟着换）。
★ **量纲三者不可互相顶替**：口径是「毫粮/人·**120 天**」、天数是「**天**」、`Industry.cycleDays` 是「**该产业的**一周期几天」。

### ② 清零落在**新周期第一天**，不在关账那一支 ★★ 控制器骨架在此处是错的

骨架说"在 `progressed >= cycleDays` 那一支里把本期字段归零"。**照做会出事**：那一支**自己**就产生本周期最大的一笔所得（收获的毛产分配）⇒ 在那里清零等于把刚收获的那笔当场抹掉，**关账日读到的 `income` 是 0**，而 V5 判据要的正是关账日读到**整周期**的量。
⇒ 改成**新周期第一天**（`progressDays() == 0`）起整行从 0 重记。语义 = spec 原文的"周期结算后**归档/清零**"：关账日读得到（归档），次日从 0 起（清零）。
★ 现成先例在同一段代码里：`unmetNeed` 早就是这个形态，且被既有用例逐值钉着。
★ 粒度仍是**按产业、按周期** ⇒ **§十一 等价性（一次 N 天 == N 次单日）不受影响**（清零点由 `progressDays` 决定，它是天数的纯函数）。**这条要显式验收。**

### ③ 分配残差"与 `splitByShares` 统一"要落成**真事实**，不是一句注释

事实核查：`splitByShares` **现在不是**最大余数法——它把残差按**索引序**逐个 +1（`EconomySeeder` 的 `splitByShares` / `splitProportional` 都是）。
⇒ 只改 `distributeResidue` 再写句"已统一" = 本仓最忌的**假统一**（"注释声称有、其实没有"的同族）。
⇒ 真统一：规则定为**最大余数法**（余数大者先得，**同余数按索引序**）；**分母各自不动**（`splitByShares` 分母恒 1000‰ 且带一条**故意的**报警行为——比例表被改坏 ⇒ Σ ≠ total，有既有用例钉着；`allocate`/`splitProportional` 的分母是 **Σ权重**）；加一条**跨模块一致性用例**（`allocate ≡ splitProportional`，同一组输入逐值相等）⇒ `allocate` 升为 `public`。

### ④ §八.8 选 (i)：结算写 `ClassRow.naturalNeeds`，读口读它

另一案 (ii)"读口改用人口 × 口粮系数"**物理上做不到**：读口是 `ApiViews.economyHex(HexCoord, EconomyData)`，**入参没有 tick**；而 ① 之后"当日需求"是**绝对日的函数** ⇒ 读口不可能复算出结算当天那个数。
⇒ 字段是唯一能承载它的地方。字段名、形状、JSON 键**全不变** ⇒ 前端不用改取数。
★ 代价如实记：读口显示的是"**最近一次结算那天**"的需求（两次结算之间不刷新）。测试按"结算完立刻读"钉住。

### ⑤ 致死率的旋钮用**包内可见重载**，不用 `static final` + `if`

`static final int = 0` + `if (常量 != 0)` ⇒ 非 0 那支是**编译期死代码**，永远测不到（spec §3.2 与 plan2 偏离③点名的同族）。
⇒ `settle` / `settleOneDay` 收一个 `famineMortalityPerMille` 参数（包内可见），公开入口喂默认 `0`。
★ `applyFamine` **不删**（「先不做」= 默认不生效；「项目代码应当是自由的」= 旋钮要在）。★ `FlowRow.deaths` 的注释要写明"默认路径恒 0"，本仓禁"看起来在记、其实永远 0"的静默字段。

### ⑥ V4 的"读口暴露"**已经存在**，别新增字段

事实核查：`ApiViews.flowView` 已发出 `unmetNeed` 与 `deaths`，`classRowView` 把 flow 整份挂进每行。
⇒ 不新增 hex 级聚合（新增求和键 = 多一处读数面，而 ④ 要的是**少**一处真相）。只做两件：`flowView` 注释点明 `deaths` 默认恒 0；端到端加一条"缺粮 ⇒ 读口读到非 0 `unmetNeed`、且 `deaths == 0`"的用例。

## 本批不做（留白有理由，不是遗漏）

1. **参数目录（V7）**：致死率 / 口粮系数 / 播种次序仍是"具名常量 + 包内可见重载"，注释写明"V7 迁入参数表"。**不造半套目录**。
2. **不另存累计流水**（spec §八.5 提的"累计量另存"）：别再造"看起来在记"的影子字段；周期末的数在关账日的 revision 里读得到。
3. **不改读口契约**（不加 tick 参数，会破 GUI/MCP 与前端门禁）。
4. **真档 240 天只做 1 格量级**（14,806 人那格）；799 格全推 240 天是几十秒级纯计算，而"流水是本期的量"在**逐行恒等式**上已不可能更真。
5. **`panels.js` 里"1000 亩/格 × 地形系数（平原 1.0 / 低丘 0.6）"那句过期提示本批不改**（不属 V4/V5；V2 标定后应是 3,100 亩 × map 的 `food`）。**记录，留给下一批。**

## 验收判据（可执行）

- **V4**：致死率默认 `0` ⇒ 人口**一个不少**；传 `200‰` ⇒ `deaths` **逐值可预测**（这条路要被真断言，不是死分支）。
- **§八.6**：120 天的 Σ 日耗 **== 人口 × 10,000 毫粮**（精确、不丢）；且逐日差分（不允许 `n × 某一天的量`）。
- **§八.5**：推 240 天 ⇒ 关账日的 `income` 是**一个**周期的量（不是两个）；次日读到的本期字段从 0 起。
- **§八.7**：`allocate ≡ splitProportional` 逐值相等；地主不再拿"均摊后远高于权重"的那一份。
- **§八.8**：读口 `grainDailyConsumption` **== 结算当日实吃**。
- **§十一 等价性**：一次 N 天 == N 次单日，**终态逐值相等**（清零是周期末的确定性操作，不得破坏它）。
- **守恒**：`Δ库存 == 所得 − 消费` 逐行恒等。

## 铁律

- **不许放宽断言**。本轮唯一合法的改法是"**按新口径重算期望值**"（算式写进注释）与"**修夹具**"（夹具自身违反新口径时）。禁止把 `isEqualTo` 降级成 `isPositive`/`isNotEqualTo`。
- **期望值优先写成由常量推出的算式**；多日口粮一律经 `EconomyVocabulary` 的公开纯函数表达，**不许写 `n × 某一天的量`**。
- **每条护栏配变异自证**：改坏判据 ⇒ 必须红 ⇒ 用 **Edit 反向重写**还原（**不许** `cp`）⇒ 复绿，`git diff` 应为空。
- ★★ **判别力声明必须真的成立**：凡写"由 X 承担判别力"，X 必须**存在**且**真的会红**。（控制器犯过两次：**幻影判别力**——注释声称某用例存在而它根本不存在；**假判别力**——声称"系数失效它会红"而实测不会。）写完逐条自查。
- **一次只能跑一个 Maven**（`pgrep -af "surefirebooter|classworlds.launcher"`）；判过不过看 `target/surefire-reports/*.txt` 的 **mtime 落在本轮**，不看 rc。
- 改完跑 `./mvnw -q spotless:apply`；若它动了你没改过的文件，**停下报告**。
- **不要 `git commit`**（控制器统一提交）。**不要**改本批范围外的文件。

  ① `EconomyAllocationConsistencyTest` 守的是"两个入口仍同一份口径"，**不是**"残差规则是最大余数法"
  （把规则改回按下标序时两边同变、它保持绿；规则由 `ProportionalSplitTest` 等三条守）；
  ② `EconomySettlementTest.allocate…` 原写"分母错时 Σ ≠ total"——**实测分母错时 Σ 仍 == total**，该句已改。
- **真实缺陷（非变异）**：verify 首轮 SpotBugs 报 `UPM_UNCALLED_PRIVATE_METHOD`（私有 3 参 `settleOneDay`
  因改走 5 参重载而无调用者）⇒ 删除后 verify 复绿。（控制器在它的报告到达前已从 IDE 诊断里看出这条并要求实测。）
- ★★ **需控制器复核的语义改动（已核，批准）**：`allocate` 的**分母**由恒定 1000‰ 改为 **Σ权重**。
  逐项验算：`allocate(5,950,000, {464,354,144,36})`，Σw=998 ⇒ 新 `{2,766,333, 2,110,521, 858,517, 214,629}`，
  与实现者给的一致；旧值 `{2,763,775, …, 217,175}`（残差均摊 ⇒ 地主拿 2,975 而应得 429）。
  批准理由：只有分母改用 Σ权重，§八.7 的两条判据（"地主不再拿 7 倍" + "`allocate` ≡ `splitProportional` 逐值相等"）
  才能同时成立——分母不同的两个函数不可能逐值相等。`splitByShares` 保留恒定 1000‰ 是**另一件事**
  （其权重按契约即千分数，Σ ≠ 1000 属数据错误、要报警），"统一"只覆盖**残差规则**，已在报告与注释里如实写明。
