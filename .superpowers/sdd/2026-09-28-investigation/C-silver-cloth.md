## 〇、三条口径，先说清（否则下面每个数都会被读错）

1. **银：只能做存量归因，不能做流水归因。** `ProductionLedger` 是**一天一本**：它在
   `PopulationEconomyTimeParticipant.simulateWorld` 里是循环内的局部变量（`:209`），当天就 `OwnershipBooks.fold` 折成
   actor 条目（`:212`），**不落进任何 ChangeSet / revision**（提案只带 `EconomyChangeSet/SocialChangeSet/ActorChangeSet`）。
   进程内 `MarketReportFeed.publish`（`:211`）也**不落盘、重启即失**（读口 `unavailable.matchResults` 具名同一件事）。
   ⇒ "谁付给谁"的逐笔流水在年度推进结束后**已不存在**；本报告只能给"期初/期末持有量"的存量归因。
2. **市场读数是"读时现值"，不是订单时刻的账。** `marketReadout.supply/demand/naturalNeed` 是 dump 那一刻由
   `MarketReadout.derive` / `planOrders` **现算**的（`MarketReadout.java:36-45, 190-215`）；`match.*` 来自**最近一次开市**的
   进程内 `MarketReport`（当日 180/360 的那一轮）。两者窗口不同，下面凡用到都分列。
3. **`naturalNeeds` / `effectiveDemand` 不参与订单。** 订单量来自"人口 × 35 天生活保留"（家户）或经营者必要投入
   （`MarketSettlement.ordersFor :679-748`、`householdLifeReserveOf :1727-1739`）+ actor 侧可花银（`:723-731`）。
   `naturalNeeds` 的唯一写点是 `EconomySettlement.withDailyNeed`（每天消费前覆写，`:4321`）；`effectiveDemand` 在 main 里
   **没有结算写入点**（只创世写空表 + 载荷原样透传）。⇒ 本报告的需求量一律按 35 天生活保留口径算；dump 里那两栏只当
   "读数"引用并注明不参与订单。★ 与调查 D 的控制方同步一致。

### 1.4 为什么不能把"净去向"写成"流向"（机制核实）

- `ProductionLedger` 当日丢弃、未持久化（§0.1 的代码位置）。store 里 `events` 表只有命令生命周期事件，无转移流水。
- 制度模板里**工资/地租/分成全是实物**（`RegimeRelations`：feudal 粮、household 布、tenant 粮；handicraft 有一档
  `FIXED_MONEY_WAGE`，但"付方可见货币为 0 ⇒ 实付 0"；201 本 craft 账 @360 合计只有 214 毫，全年量级不可能解释 7.17M）。
- 本年度债务**全部是粮债**：dump 的 `debtDetails` 222 条(@180)/1398 条(@360) 的 `commodity` 全 = `grain`，
  无一条银债。⇒ 银的换手**只剩市场成交一条通道**（`TransferReason.MARKET_TRADE`）。
- 所以能坐实的是：**这 7,173,772 毫银是城镇买家在市场里付出去的净额**；其**净**落点是农村（+6,684,360）与经营者
  （+489,412）。但"哪一笔从哪个城镇买家付给哪个农村卖家"无法从期末账复算。间接佐证是市场报告：@180 粮成交
  2.22B（本调查复算）/ @360 63.0M 量级，而布成交只有 15.9M / 0.196M；城市现金主要在买粮。★ 这仍是间接证据，不是流水证明。

- ★ `needsButCannotAffordMilli` 对布**恒 0 是代码结构性**：`MarketReadout` 只对粮算它（`boolean grain = ...; if (grain) {...}`，
  `MarketReadout.java:234`）。**不能**把布的 0 读成"都买得起"。
- ★ 布的自然需要只有"一天"窗口（`naturalNeedWindow=last-settled-day`），`cycleNaturalNeedMilli` 恒 0（非粮无累加器）。
  35 天口径的自然需要 = Σ`cumulativeClothMilli(pop,35)` = **1,107,022,544**（@360；@180 为 1,097,293,974），
  对照 30.86B 的供给 ≈ **27.9 倍**。
- ★ **供给恒等式（逐毫对上）**：`supplyMilli = Σ家户 max(0, 布库存 − 35天生活保留) + Σ经营者布库存`
  - @360：16,602,719,737 + 14,261,601,626（weave 12,135,680,483 + craft 2,125,921,143）= **30,864,321,363**。
  - @180：5,920,377,749 + 5,351,243,246（weave 4,387,827,756 + craft 963,415,490）= **11,271,620,995**。
  ⇒ 布市场是"农村家户把实物资收入挂出来 + 两个经营者账户挂出全部存货"；经营者侧布的保留/必要投入 = 0。

`target = ⌊pop × 1000 × 35 ÷ 365⌋`（`EconomyVocabulary.cumulativeClothMilli`，`:177-184`）；
`available = max(0, 布库存 − frozenGoods)`（frozen 本快照 = 0）；`gap = max(0, target − available − confirmedIncoming)`；
订单还要 `可花银 > 0` 且 `quantity = min(gap, ⌊可花银×1000÷参考价⌋) > 0`（`ordersFor :679-748`）。

### 2.3 ①~⑤ 分解（每项给算法与数）

**① 无需求 / 保留已足（农村的主导项）**
- 算法：`gap = max(0, target−(库存−冻结))`，target 见 §2.2。
- 数：**3,195 / 3,196 = 99.97% 的农村行 gap=0**（@180 为 3,196/3,196）。全部 3,196 个农村行的
  `naturalNeeds.cloth > 0`（人口>0 的行都有布需求；"naturalNeeds 没有布"**不成立**——但按 §0.3 它本来也不进订单）。
- 唯一 gap 行只差 192 毫匹 ⇒ 本项解释了农村"不买布"的 **99.97% 以上**。根因是实物收入堆积（§2.2），不是需求口径缺失。

**② 无预算（农村：0 行；城镇：量级限制）**
- 算法：`gap>0` 且 `可花银 = max(0, money−frozenMoney) ≤ 0` ⇒ `continue`，订单根本不下（`:723-731`）。
- 数：农村 **0 行**（唯一 gap 行有 112,147 毫银）。所以"无预算"**不能**解释农村。
- 但它是布市场不闭合的另一半：@360 有 gap 的 265 个城镇行合计只有 **902 毫银**（77 行 × 2 + 184 行 × 4 + 4 行 × 3），
  读时订单量 178,021（1.67% 的 Σgap 10,656,502）；而持有城镇 99.3% 银的城镇地主（229,565）恰恰没有布缺口。

**③ 价格 / 限价（0 行被挡）**
- 算法：`reference = market.priceOf(cloth)`；`bid=⌊ref×990‰⌋（≥1）`、`ask=⌈ref×1010‰⌉`；区内撮合要求
  `ref ≤ 买方 maxLandedPrice(=ask)` 且 `ref ≥ 卖方 minPrice(=bid)`。
- 数：799 格布参考价**全部 = 5**，`bid/ask = 4/6`（201 区全同）。按构造 `bid ≤ ref ≤ ask` ⇒ 区内限价过滤**恒通过**。
  跨区过滤用卖方参考价 + 到货时限，`freight` 因无 ORGANIZATION 承运主体恒 0（报告已记）。**没有 1 行因限价被挡**。
  唯一的"价格副作用"是整数粒度：参考价 5 时，2/4 毫的预算折成 400/800 毫匹。

**④ 订单生成（取整 0：0 行；字段：`effectiveDemand` 从未被写；撮合口径另有 2 毫保证金）**
- 算法：`quantity = min(gap, ⌊budget×1000÷ref⌋)`，`quantity ≤ 0` 就不下单。
- 数：gap>0 且 budget>0 时 quantity 必 >0（budget≥1 ⇒ ≥200 毫匹）；**没有"取整为 0"的行**。
- `ClassRow.naturalNeeds`：有布（人口>0 行全有；2,392 个城镇零人口行的空表是正确空表）。
- `ClassRow.effectiveDemand`：**6392 行 × 两个 tick 全是 `{}`** —— main 里没有写点（`withDailyNeed` 等方法原样透传
  `row.effectiveDemand()`，`:4321/4338`）；读口 `marketReadout.effectiveDemandMilli` 是**读时经 `planOrders` 现算**的，
  不是这个字段。
- **真正压住城镇需求的是撮合侧的 `MARKET_MONEY_ROUNDING_MARGIN_MILLI = 2`**（`:159`）：`affordableQuantity` 先
  `money − 2` 再折数量（`:1443-1452`），而订单生成不减这 2 毫。读时口径：订单量 178,213，但按撮合算式最多只能成交
  **74,145**（58.4% 永远成交不了）：77 行的 2 毫 ⇒ 撮合可买 0；184 行的 4 毫 ⇒ 只能买 400（订单 800）；4 行的 3 毫 ⇒ 200（订单 600）。
  这与会话里真实的"买方未成交 267 笔 / 464,160 毫匹（全部 `algorithm_uncovered`）"方向一致（窗口见 §2.5）。
  ★ 这是"订单生成与撮合两套可付口径不一致"的事实，不是本轮的设计裁定。

**⑤ 市场可达性（不是约束）**
- 算法/读数：`match.unfilledBuyCounts/SellCounts` 按 `regionId` 去重统计。
- 数：@360 布**没有** `no_adjacent_supply` / `no_seller` / `all_reserved` / `price_limit` / `logistics_*` 任何一个；
  买方未成交只有 `algorithm_uncovered` 267 笔，卖方只有 `no_budget` 4,721 笔。@180 卖方全是 `no_buyer` 3,479 笔。
  `unusedCapacityMilli` @360 合计 7.997e12（跨区候选路线大量闲置运力，`freight=0`）。
  ⇒ 布卖不掉/买不到**不能归因于区可达性**。
- ★ 读数警告（回代码核过）：卖方 `no_budget` 的判定是 `collectUnfilled :1585-1594` 里**全局** `anyBuy`——
  只要全世界（不限同区/邻区）还有一笔同商品未成交买单，就给所有剩余卖单盖 `no_budget`。因此 4,721 这个数**不能**
  读成"本区有买得起的人没成交"；它只表示"卖方有余、且世界上有未成交买单"。

### 2.5 两处必须同时说的窗口/复算差异

1. **读时 ≠ 开市时**：@360 读时订单量 178,213，而那一轮开市的未成交买单是 267 笔 / 464,160（成交 196,119）；
   @180 读时订单量 0，而那一轮成交了 15,902,560。原因是读时读数在**结算日结束之后**按当时余额重算，而 `match` 是
   当天开市那一刻的报告；城镇余额在当天买粮后只剩 2~4 毫，所以读时订单量被压得更小。**看"为什么没生成订单"用读时口径；
   看"实际成交/未成交"用 match 口径，两者不可混算。**（180 那 15.9M 布的买家/卖家明细不可得——ledger 已丢。）
2. **原报告的 208 区 / 布成交 224,004 与两份 dump 不可复算**：本调查按 `regionId` 去重得 **201 区**；
   创世 seed 的 `SocialCity` 恰为 **201 座**（德 108 + 奥 33 + 霍 60，anchor 全在 799 格内，逐条从 store revision 2/3/4 核过），
   `MarketTopologyBook` 一城一区 ⇒ 201 个市场区。同一去重口径下 @360 布成交 = **196,119**（@180 = 15,902,560）。
   报告 §4.1 的 208/224,004 来源未查明，本文所有市场数一律用可复算的 201 区口径；两者差 **27,885** 毫匹，**未当成事实使用**。
