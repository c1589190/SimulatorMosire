## 1. 节点地址：`treeXXX-tickXXX`，弃用 rev

用户补裁：

> 「额，我觉得可以重写成treeXXX-tickXXX，弃用掉rev，因为后面总是要兼容通用的分支切换的，让节点版本跟着tick是非常坏的」

设计裁定：

1. 节点地址使用 **`treeXXX-tickXXX`** 形式（例如 `tree1-360`、`tree1-0`）。
2. **弃用 rev**：不再用“同一 tick 内的 rev1/rev2”表达节点版本。
3. **版本由分支表达**：同一 tick 想要另一个版本 ⇒ 新建一个分支（如 `tree2-0`），而不是在同一 tick 下挂多个 rev。
4. 将来必须兼容**通用分支切换**；节点版本不得绑定在 tick 上。
5. 一个 `(tree, tick)` 对应**一个节点**；节点之间的关系由分支/父节点表达。

**工程待定**：

- `treeXXX` 的命名规则（是否只允许 `tree` 前缀 + 数字；是否允许用户自定义分支名）；
- `tick` 的格式（十进制整数；是否允许负 tick / 非连续 tick）；
- 旧 `branch/revision` 地址的兼容/迁移；
- 节点表形状（`(branch, tick)` 主键？父节点引用？节点增量/checkpoint 归属？）。

## 2. 2+1 模式确认：战役是 +1，阶段是独立地址

用户补裁：

> 「对，因为战役的每个阶段都是可以独立编辑的，相当于独立地址，这里还有从军队-战役系统到文档系统的GUI映射」

设计裁定：

1. **2 个核心大模式**：地图编辑、单位编辑。
2. **+1 = 战役编辑**（战役系统由 army 模块维护；前端可下放 army 模块）。
3. **战役的每个阶段都是独立可编辑实体，拥有独立地址**：
   - 现有 `army:combat.<id>:stage.<sid>` 已具备基础；
   - 阶段编辑需要独立命令/工具，而不是只能 append/resolve。
4. **军队—战役系统到文档系统的 GUI 映射**：
   - 战役/阶段的自然语言内容（战报、过程、叙述）由文档系统承载；
   - GUI 在战役/阶段详情里展示“该地址是否有文档、有多少文档、打开文档”的入口；
   - 文档地址与战役/阶段地址的映射必须标准化。
5. 区域编辑并入地图编辑（前端可由 `simos-map` 模块提供），不作为独立大模式。

## 3. 自然语言记录的所有权：只有文档系统负责

用户补裁：

> 「是的，其他部分代码只负责储存数据结构，只有文档系统负责储存所有自然语言记录，懂我意思吗？」

设计裁定（硬边界）：

1. **领域模块只存结构化数据**：稳定 ID、地址、枚举、数值、时间、引用关系等。
2. **所有自然语言记录由文档系统统一存储**：描述、备注、战报、经过、说明、叙事、历史记录等。
3. 领域模块需要“自然语言内容”时，**存的是文档地址（或可解析到文档地址的引用）**，不是正文本身。
4. GUI 的“看/写自然语言”入口统一走文档系统；领域模块 GUI 只负责结构化字段编辑与文档入口映射。
5. 文档系统必须能按“实体地址 / 部分地址 / 模块名称”查询，并支持多版本、多名称、删除回收站、编辑备份。

**必须审计的现有自然语言字段（初步，待逐项核）**：

| 现有字段 | 位置 | 处置方向（待设计） |
|---|---|---|
| `RegionMeta.description` | `simos-map/.../RegionMeta.java` | 迁到文档系统，meta 只留结构化 tag/color/annexedBy |
| `CombatRecord.text` | `simos-army/.../CombatRecord.java` | 改为阶段/战役的文档地址 |
| `CombatStage.text` | `simos-army/.../CombatStage.java` | 改为阶段文档地址 |
| `Unit.stateDescriptions` | `simos-unit/.../Unit.java` | 已是“状态→地址”链接，可作为文档地址引用继续 |
| `DecisionInfoEntry.note/value` | `simos-ga/.../DecisionInfoEntry.java` | 决策文档/INFO；与文档系统关系待定 |
| `SocialCity.props` / `RegionMeta` 自由文本 | social/map | 只留结构化字段；自然语言迁文档 |

> 注：名称（`Region.name`、`Unit.name`、`Nation.name`、`Army.name`）属于**结构化标识/显示名**，不视为自然语言正文；但“别名/多名称”由文档系统的名称索引承担。

## 4. 模块保留范围

用户补裁：

> 「gov保留完整国家、外交等，ga和actor我记得他妈和经济没有直接关系吧？它表述的是决策人」
> 「……是的之后还要加决策人查看、编辑模式，但是目前任务量太大了，所以暂时放着，不和经济模块一同删除」

设计裁定：

1. **gov 保留完整**：国家、外交、GOV 单位/读数等能力不随经济一起删除。
2. **ga 保留**：决策人/决策包/INFO 等；**actor 保留**：账户/库存等；它们与经济模块没有直接绑定。
3. **决策人查看/编辑模式暂缓**（任务量原因），但**不删除 ga/actor**。
4. **暂停/卸载范围 = economy / production / culture**（以及与它们直接绑定的时间参与者/工具/种子）。
5. social 是否保留：按 gov/unit 的依赖，**默认保留**（gov 的招募/岗位等工具依赖 social）；若后续确认不需要，再单独裁。

## 5. 文档根：仓库 `docs/`，独立且持久

用户补裁：

> 「放docs，文档是独立且持久的」

设计裁定：

1. 世界文档放在**仓库 `docs/`** 下，而不是运行时 store。
2. 文档是**独立且持久**的数据：不随节点/revision 删除而删除。
3. 文档与实体地址的映射必须是稳定路径/索引；节点版本变化不应让旧文档失联。
4. 具体目录、文件名、版本/回收站/索引协议见 §8 待定项。

## 6. 清理授权

用户补裁：

> 「除了本地经济分支全都可以清理完」

设计裁定：

1. 允许清理旧的大文件、旧 worktree、旧证据、旧 store、build 产物等。
2. **本地经济分支必须保留**（分支 ref 不删除）。
3. 清理前必须先把 dirty worktree 的未提交改动保存到对应分支（WIP commit）或等价归档；不得静默丢失。
4. `.git` 历史默认不重写；`.m2-repo` 依赖缓存默认保留（除非用户另行授权）。
5. 清理后要在 `STATUS`/报告中记录释放的体积与保留项。
