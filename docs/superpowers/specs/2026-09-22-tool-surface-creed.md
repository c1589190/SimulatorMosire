# 下一阶段开发宗旨：工具面标准化

> 用户 2026-09-22 裁定。**这是宗旨（原则），不是计划**——细节留到计划里写。
> 一句话：**领域数据标准化呈现为工具；工具同源，一次定义多处可用。**

## 一、同源

**GM Tool 与 MCP Tool 是同一份东西。**

- 一份 `AgentTool` 定义 ⇒ `SimosToolSource` 按 `Role` 分桶 ⇒ **MCP 只是把桶导出去**
- ⇒ **给某个桶加一条工具 = 该面上自动出现**，**不需要为 MCP 另做一套**
- ⇒ 缺口从来不是"没挂载"，而是"**工具本身不存在**"（`SimosToolSource.java:47-64` 的分桶就是现状）

## 二、全覆盖

**`map` / `social` / `unit`（以及 `sd`）的【所有数据】都应当如此标准化呈现。**

- **读与写都算**（不只是写命令）
- ⇒ 一个领域命令／读口 ⇒ 一条对应的 `AgentTool`
- ⇒ 现状差距很大：`map` 7 写 + 3 读、`unit` 21 写、`sd` 16 条，**绝大多数没有工具** ⇒ 只能经 `simos.command.submit`（通用写）

## 三、前置即错

**缺前置 ⇒ 报错，不静默兜底。**

- 例（用户原话）：`sd.CreateArmy` —— 「**如果有对应 Nation/Army 就正常，没有就报错**」
- ⇒ 工具层要做**前置校验**，失败要**可读的理由**，不许静默返回成功/空

## 四、与既有裁定的关系

- **D2 已裁**：现有 MCP 口 = `EXTERNAL ∪ GM`、**保留通用写**（★ 与 N9 的冲突已在 `SimosToolSource.java:59-61` 记账）
- ⇒ 标准化是**并存**，不是替换；**"通用写是否收窄"列为开口项**（等标准化覆盖够了再议）
- ★ 参照 N9：**决策人只给窄工具、不给通用写**

## 五、老规矩（不变）

- 每加一条命令/工具 ⇒ **连带改**：`CatalogTool.PAYLOAD_HINTS`（缺项**构造期抛**）+ `McpCoverageTest` 的双向载荷断言（★ 只注册不补载荷**必红**）
- **每条护栏要能被变异杀掉**；**门禁绿**；**证据落位**；★ **一个 key/密钥不许进代码**
- ★ **权限是设计的一部分**：哪个工具归哪个桶（GM / 决策人 / 外部）要**明确写出来**，不是默认
