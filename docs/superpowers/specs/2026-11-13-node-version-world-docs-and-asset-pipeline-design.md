## 1. 节点版本与时间线存储（补裁）

### 1.1 历史节点写入：保持“不改历史”，要改地图就开新节点

用户补裁：

> 「那就保持，想要改地图单开一个节点，反正都是开创造，什么时候开不重要」

设计裁定：

1. 现有“只能对 head 写”的约束**保持**；不实现“原地重写历史节点”。
2. 要修改某节点地图 ⇒ **新开一个节点/分支**，在新节点上编辑。
3. “开创造”的时机不受限制；节点可以随时创建，不要求先推进时间。

### 1.2 分叉：任意节点都可分叉

用户补裁：

> 「改，只要是节点就允许根据状态分叉」

设计裁定：

1. 分叉不再只限 head；**任意已存在节点**都可以作为分叉点。
2. 分叉产生的新分支/节点以该节点状态为父，后续推进独立。

### 1.3 中间 revision：物理删除/压缩

用户补裁：

> 「直接打死，顺便把老的大文件清理一下，它们没！用！了！」

设计裁定：

1. 节点之间的中间 revision **不再长期保留**（物理删除/压缩；具体机制待工程细化）。
2. 只保留**节点级**状态/增量；节点是时间线的最小持久单位。
3. 旧的大文件（历史 store、证据、临时产物等）可以清理；清理范围与安全边界待工程列出清单后执行，不得误删未推送的源码成果。

### 1.4 节点身份：tick + revision，允许多版本

用户补裁：

> 「允许单一tick有多个版本的节点，选一个版本节点推进，也就是tree1-0tick改成0tick-rev1/xxx、0tick-rev2/xxxx，相当于分叉了，这样一来是否推进时间都和节点解耦了」

设计裁定：

1. 同一分支同一 tick **允许多个版本节点**。
2. 节点地址必须包含 **tick + revision（版本）**，例如：
   ```text
   0tick-rev1/...
   0tick-rev2/...
   ```
3. 用户可以**选择一个版本节点**继续推进；不同版本节点等价于分叉。
4. **推进时间与节点创建解耦**：创建节点不必然推进 tick；推进 tick 也不必然创建多个中间节点。

> 注：`0tick-rev1` 的精确语法、`tick`/`rev` 的顺序、是否保留 `tree1` 分支前缀作为外层，属地址语法待定项（§9）。

## 2. 模式：2+1 大模式

用户补裁：

> 「改成2+1大模式，后续不排除多加，其中对于战役系统的维护前端、区域编辑前端可以下放到相关模块，确保模块语义正确」

设计裁定：

1. GUI 从当前六模式收敛为 **2+1 大模式**，后续允许扩展。
2. 战役系统维护前端、区域编辑前端**可以下放到相关模块**，以保证模块语义正确。
3. 模式仍是 GUI 面概念；工具面只有工具组（D-034 §3.1 继续有效）。

**待定（§9）**：“2+1”的精确拆分。当前有两种读法，需要用户补一句确认：

- 读法 A（按上下文更可能）：**2 个核心编辑模式 = 地图、单位**；**+1 = 战役**（战役前端由 `simos-army` 提供）；**区域编辑并入地图编辑**（前端可由 `simos-map` 提供）。
- 读法 B：2 个核心编辑模式（地图、单位）+ 1 个尚待命名的扩展位，战役/区域都只是模块子前端。

无论哪种读法，**区域编辑并入地图编辑**、**战役前端可下放给 army 模块**、**单位类型小窗由对应模块提供**这三条不变。

## 3. 经济及相关模块：卸载挂载与调用

用户补裁：

> 「直接把经济模块的挂载、在app中、其他模块中的调用暂时删除就行，让时间推进时经济模块和其他相关模块不动即可，目前暂时只做好地图、区域、单位、军队、政府以及app和各自的GUI部分、统一的GUI和时间线推进等」

设计裁定：

1. **暂时删除**经济模块在组合根中的挂载，以及 app/其他模块对经济模块的调用；不是“保留装配但隐藏 UI”。
2. 时间推进时，经济模块及其他被暂停模块**不参与**（不产生变更集、不写状态）。
3. 当前产品范围收敛为：
   - 地图 / 区域；
   - 单位 / 军队 / 政府单位；
   - app 与各模块 GUI；
   - 统一 GUI；
   - 时间线推进。
4. 暂停范围至少包括 economy、production、culture；social / actor / ga 是否也随之下线，按 §9 待定。
5. 旧模块代码/旧设计不删除，保留为将来恢复的基础；但**不挂载、不被调用**。

## 4. 世界文档系统（按地址的 md 文档）

用户补裁：

> 「因为对于每一个程序化地址都可以在docs下指定一个md文件，里面写东西；删则是把旧的文档放到回收站文件夹里，标删除日期；改则是先备份旧的，再添加新的；插则是可以选择根据地址查、根据部分地址查、根据各个模块中地址的对应名称查」
>
> 「一个地址可以对应多个版本多个名称的文档，都是需要可以查询的，这方面肯定还是需要标准化协议配合」

设计裁定：

1. **每个程序化地址**都可以对应一个 md 文档，放在 `docs` 下。
2. 基本操作：
   - **增**：创建该地址的 md；
   - **删**：旧文档移入**回收站文件夹**，并标记删除日期；
   - **改**：先**备份旧文档**，再添加新文档；
   - **查/插**：可按完整地址查、按部分地址查、按各模块中地址对应的名称查。
3. **一个地址可以对应多个版本、多个名称的文档**，都必须可查询。
4. 需要**标准化协议**：地址、版本、名称、删除日期、文档路径、模块归属等字段必须有统一约定。

**待定（§9）**：

- `docs` 指仓库根 `docs/` 还是运行时 store 下的 docs 根；
- md 文件与地址的映射规则（路径派生/索引表）；
- 版本/名称/删除日期的存储位置（frontmatter、sidecar、索引文件、还是日志型存储）；
- 回收站目录名与保留期限；
- “按模块名称查”的模块名/别名注册协议；
- 是否复用 `docs-mosire` 的 LOG/FILE 纪律与 `DocEntry` 多版本模型。

## 5. PNG 网页底图与地形提取

用户补裁：

> 「地图编辑模式还应该加入一个网页底图，就是允许载入一张png图片，然后把图片和指定hex（本质六边形图形）的像素对应，然后每个hex的中心取像素颜色来实现提取地形等策略，不过这个就得等架构修改完再说了」

设计裁定：

1. 地图编辑模式增加**网页 PNG 底图**：载入一张 PNG，作为地图背景显示。
2. 允许把图片像素与**指定 hex** 对齐（指定参考 hex / 缩放 / 偏移）。
3. 对每个 hex，取**中心像素颜色**，据此提取/推断地形等数据。
4. 该功能**排在架构修改之后**实现，不在本轮重构范围内。

**待定（§9）**：

- 对齐方式（选 2 个参考 hex 定缩放/偏移？选 3 点仿射？手填 offset/scale？）；
- 颜色→地形的判定（精确匹配 TerrainCatalog 颜色；最近色；容差；自定义调色板）；
- 采样点（严格中心 / 多点平均 / 排除描边）；
- 提取结果的应用方式（一条 `map.SetTerrain` 按地形分组批量写？预览后确认？）；
- 底图是否随节点/地址持久化，还是仅编辑期临时视图。

## 8. 验收方向（待工程细化）

1. 任意节点可分叉；分叉后两个分支的推进互不影响。
2. 同一 tick 可存在多个版本节点；选择一个版本推进后，其它版本不变。
3. 节点地址（如 `0tick-rev1/...`）可稳定解析到唯一节点。
4. 中间 revision 被清理后，节点仍可回放/读取，且体积明显下降。
5. 时间推进不触发经济/生产/文化等暂停模块。
6. 三模式（或 2+1）在 GUI 可进入；区域编辑/战役前端由对应模块提供且语义正确。
7. 每个地址可创建 md；删除进回收站并带日期；编辑先备份；可按完整/部分地址和模块名称查询多版本/多名称。
8. PNG 底图可加载、可对齐；按 hex 中心颜色提取地形；提取结果可预览/应用。
9. 旧文档/旧模块仍可在需要时恢复，不被本轮清理误删。

## 9. 未定项

1. “2+1”的精确拆分（读法 A/B）。
2. 暂停范围是否包含 social / actor / ga；`gov` 是保留完整模块还是只保留政府单位能力。
3. 节点地址语法：`0tick-rev1` 与 `tree1` 分支前缀的组合方式；是否保留旧 `branch/revision` 地址兼容。
4. 中间 revision 的删除/压缩机制：删除范围、节点表形状、回放保证、旧档处理。
5. 旧大文件清理范围与安全线（哪些 worktree/证据/旧 store 可删，哪些必须保留/归档）。
6. 世界文档根：仓库 `docs/` vs 运行时 store；md 路径派生与索引。
7. 文档版本/名称/删除日期的存储协议；回收站目录与保留策略。
8. 文档查询的“部分地址”“模块名称”匹配规则（前缀/分词/别名表）。
9. PNG 对齐与颜色→地形算法；底图是否持久化。
10. 模块前端下放的资源机制（模块自带静态资源、脚本注册、页面装配、权限边界）。
