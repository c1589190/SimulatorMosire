## 1. 产品定位

当前项目（SimulatorMosire / simos）在本次收敛中定位为：

1. **文游地图编辑器**；
2. **数据保存处理器**。

不是“先把完整政治经济军事模拟跑通”，而是先把“时间线 + 地图/单位/战役编辑 + 可按地址查询的数据”做成可用的产品面。

---

## 2. 状态机：时间线节点与增量存储

### 2.1 状态机 = 时间线

- 项目只有**一个状态机**：时间线。
- 时间线允许**简单的节点式分支分岔**。
- 分支/节点是数据存储和查询的第一坐标；任何实体查询都应能落到“某分支的某节点”。

### 2.2 增量存储语义（用户口径）

以用户给出的例子为准：

```text
tick0                存一张全图数据
tree1-tick360       只存 tick360 相比 tick0 的增量（增加/修改部分）
                     tick0~tick359 的状态不单独保存
tree1-tick720       只存 tick720 相比 tree1-tick360 的增量
tree2-tick600       从 tree1-tick360 分叉；只存 tick600 相比 tree1-tick360 的增量
                     tree2-tick600 与 tree1-tick720 无关
```

**设计裁定（用户已给）**：

1. 基线节点（如 tick0）保存完整状态；
2. 后续节点只保存相对**父节点**的增量（增加/修改部分）；
3. 分支从既有节点分叉，分支节点只保存相对**分叉点**的增量；
4. 不同分支的后续节点互不影响。

**工程待定**（不在本次用户口径内，需后续细化）：

- “增量”的粒度（按实体/按字段/按 ChangeSet/按 patch 文本）；
- 删除、重命名、移动在增量中的表示；
- 基线节点是否允许替换/重写；
- 增量链的回放、压缩与校验方式。

### 2.3 地图编辑对“底图节点”的修改

- 地图编辑模式在**所有格式化节点**都可以进入，修改的是**当前节点**的地图。
- 如果修改的是已有后续节点的早期节点（用户原话举例为 tick0），视为**修改节点底图**。
- 用户要求提供一个**额外的数据合法性确认检查机**，确保修改底数据后其他节点数据不冲突。

**工程待定**：检查机的判定范围（仅结构冲突，还是业务引用冲突）、失败时的处置（拒绝/提示/自动重放）、以及“格式化节点”的准确判定。

## 3. 三种 GUI 编辑模式

### 3.1 模式的定义边界（硬约束）

- **“模式”在工具调用面不存在**；模式纯粹是**方便用户操作的 GUI 面设计**。
- 在工具层面，一个模式可以理解为一组**工具组（tool group）**。
- 同一套数据/命令必须同时可被人和 AI 使用；GUI 模式只是过滤与操作编排，不得成为第二套权限/数据真值。

### 3.2 地图编辑模式

编辑对象是 **map 包**，包括：

1. **逐格地形**；
2. **格与格之间的各类连通性关系**（河流、各类道路等）；
3. **每个节点的所有标准区域**；
4. **每一种单位在地图上的存在信息**（地方国家政府、军队等）。

**标准区域**是广义概念：允许有省份、国家、地形地区记录等多种语义。地图编辑模式允许：

- 按种类筛选；
- 或直接搜索唯一的区域对应地址；
- 进行定制化修改。

**对“被其他模块大量引用”的对象的编辑边界（用户口径）**：

- 区域、单位等被其他模块大量引用的设计，地图编辑模式**只允许更改其在地图上的存在信息**：
  - 区域：覆盖多少格子；
  - 单位：所在位置；
- 也允许**删除**；
- 其他地方访问这个对应 key 时就是**空**，交给其他模块自己处理。

**模式拆分**：

- 原先混杂在一起的 GUI 区域编辑模式、单位编辑模式，现在正式拆开；
- 区域编辑归入地图编辑模式；
- 单位编辑独立成单位编辑模式。

### 3.3 单位编辑模式

- 专门负责编辑**单一节点**的单位。
- 政府组件、军队组件各自提供自己的**小窗**；各类单位种类不同，单位编辑模式还需额外提供**单个单位对应类型的编辑小窗**。
- 例：军队可以自由创建**编制节点单位**，设置**地块级独立行动或跟随**。

**工程待定**：单位类型的注册/插件式小窗契约、单位编辑与地图编辑的写命令边界、缺失被引用对象时的 UI 行为。

### 3.4 战役编辑模式

- 战役（battle）是单一节点内、可能发生在不同位置多个军队单位之间的战斗。
- 战斗本身必须发生在一个地方，因此实际上是**强跟随于单个 hex 的地块时效状态**。
- 具体行为参考当前实现与既有文档。

**工程待定**：战役实体身份/地址、战役与 Army/Unit 模块的数据所有权、单节点内多场战役并存规则、战役编辑模式可写的字段与命令。

### 3.5 “三模式”的口径

用户口径为**三个编辑模式**：地图编辑、单位编辑、战役编辑。

- 只读查看/常规浏览不计入“三个模式”；是否保留独立查看态属于 GUI 细化项。
- 现有的“区域查看/区域编辑/决策”等模式不在本次三模式口径内；它们要么并入地图编辑，要么暂不启用。

## 4. 经济/文化/生产力暂停，地址查询补位

### 4.1 暂停范围

- **经济模块暂时挂起**；
- **与经济相关的文化、生产力模块一并暂停**；
- 本次重构不继续投入经济玩法实现。

**边界**：暂停 ≠ 删除。旧设计、旧代码、旧测试不因此失效；恢复时按各自有效设计继续。暂停期间必须明确哪些模块仍被装配、哪些 GUI/工具入口隐藏或禁用。

### 4.2 替代能力：按地址查询（GSim 式）

学习老前辈 GSim 的做法：**允许就单个地址查询**。

任何实体都应有“每节点固定地址”，至少包括：

- hex 地块；
- region 标准区域；
- unit/army 军队；
- unit/gov 政府单位；
- battle 标准战斗。

**目标示例（用户原话）**：

```text
输入：tree1-360/unit/army/vg-berlin
得到：tree1 分支、360 tick、类型为军队的“柏林国民掷弹兵师”的相关信息
      包括所在位置 hex/1,1
      以及刚刚经历了 tree1-350/battle/berlinbattle 柏林战役
```

**设计裁定（用户已给）**：

1. 地址必须能表达**分支 + 节点（tick）**；
2. 地址必须能表达**类型 + 子类型 + 稳定身份**；
3. 查询结果要能带出该实体的位置/归属/最近相关事件等关联信息；
4. 主打**规范化**：同一实体在不同节点有稳定可寻址的地址。

**工程待定**：

- 地址语法（分隔符、段顺序、是否允许省略当前分支/节点、别名/旧地址兼容）；
- “最近事件”是查询时联查，还是实体记录里保存引用；
- 地址解析失败、分支不存在、节点不存在、实体已删除时的统一错误形状；
- 地址与现有 `Address`/`Resolver`/`ResourcePaths` 体系的关系（扩展还是替换）。

## 5. 数据所有权与删除语义（用户口径）

1. **map 包拥有地图存在信息**：地形、连通性、区域覆盖格、单位位置等。
2. **区域/单位等被其他模块引用的对象**：
   - 地图编辑模式只改“存在信息”，不改其他模块的业务字段；
   - 允许删除；
   - 删除后其他模块按 key 查到**空**，自行处理（不得由 map 代填、不得静默造替代对象）。
3. **单位编辑模式**才编辑单位自身的业务字段（政府小窗、军队小窗等）。
4. **战役编辑模式**编辑战役自身状态；战役强跟随单个 hex 与单个节点。

**工程待定**：删除是否需要 tombstone、跨模块引用检查由谁执行、删除后历史节点回看时如何表现。

## 7. 验收方向（待工程细化，不是本次裁定）

后续设计至少需要能回答：

1. 同一份世界，`tree1-360` 与 `tree1-720` 的增量链能否逐字段回放出一致状态；
2. `tree2-600` 从 `tree1-360` 分叉后，是否完全不受 `tree1-720` 影响；
3. 修改 `tick0` 底图后，检查机能否给出确定的冲突/不冲突结论；
4. 三模式在 GUI 上可进入、在工具面上只是工具组，且同一命令对人与 AI 行为一致；
5. `tree1-360/unit/army/vg-berlin` 这类地址能否稳定解析并返回位置与最近事件；
6. 经济/文化/生产力暂停后，剩余模块能否独立构建、启动、编辑、查询。

## 9. 用户原话（逐字，2026-11-13）

> 来说一下我的当前设计目标
> 首先就是对于当前项目（本质文游地图编辑器、数据保存处理器）应当有一个状态机三个模式
> 状态机自然就是时间线，允许进行简单的节点式分支分岔，在数据储存上应当以随时间线节点推进的增量形式储存，顾名思义就是，tick0储存一张全图数据，然后假设下一个被设置的节点是tree1-tick360，那么tick0~tick359的状态在数据上都不保存，只保存tick360相比tick0增加/修改的那部分数据，然后以此类推继续推进到tree1-tick720，那么720只储存相比1-360变化的数据；这时候可以从tree1-tick360分叉出tree2-tick600，这个tick600和隔壁tick720没关系了，同样储存相比tick360不同的数据；
> 然后是地图编辑模式，首先，所谓”模式“其实在工具调用面是没有的事，纯粹就是方便用户操作的GUI面设计，在工具层面其实可以理解为一套工具组；地图编辑模式在所有格式化节点都可以进入，修改的是当前节点的地图——如果修改已有后续的tick0，那么视为修改节点底图（可以做一个额外的数据合法性确认检查机来确保修改底数据后其他节点数据不冲突）；地图编辑模式编辑的自然是map包的地图，包括每一格子的地形、格与格的各类联通性关系（河流、各类道路等），以及每个节点的所有标准区域（标准区域在当前项目是一个非常广泛的概念，允许有省份、国家、地形地区记录等多种语义，这里的地图编辑模式允许根据种类等筛选或者直接搜索唯一的区域对应地址，来进行定制化修改），还有每一种单位（地方的国家政府、军队等）；对于区域、单位等被其他模块大量引用的设计，地图编辑模式只允许更改其在地图上的存在信息，也就是区域覆盖多少格子、单位所在位置在哪等，也允许删除，其他地方访问这个对应key那就是空的，交给其他模块自己处理；如前文所见，之前混杂在一起的gui面区域编辑模式、单位编辑模式现在正式被拆开；
