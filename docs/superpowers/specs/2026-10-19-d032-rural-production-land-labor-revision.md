## 三、调整后的目标运行序列（草案）

> 这是按“生产轮先于市场轮”重排的草案；阶段号暂沿用现有 M 命名，后续在目标设计正式修订时统一重编号。不是对当前代码的验收。

```text
M0 Social
  - Social 结算人口/年龄/劳动能力/实际温饱
  - 读取每户温饱线配置

M1 经济载入
  - 载入活家户、劳动能力、土地持有
  - 不注入独立的 naturalNeeds 需求表

M1b 进入/迁移/组织变化
  - 后到户、迁移户、土地取得/卖出后的组织重排

M2 生产轮
  - 家户按上一轮价格/工资、实际土地、实际库存、温饱线
    选择自己的生产位置（自耕、受雇、其他生产位置）
  - 自耕/经营：按实际可播种面积扣种子；没有足够种子则只种实际覆盖面积
  - 日粮按生产方式读取本户温饱线，按生产日扣除
  - 实际劳动按实际响应者计算；受雇者必须有正收益才占位
  - 生产与入库同一环节，产出归土地持有者/工资归雇农

M3 工资结算
  - 雇农只收货币工资；未付成普通家户债务
  - 不拿库存抵工资

M4 统一市场
  - 债务最先（市场轮）
  - 需求单：未耕种面积所需种子、下一轮口粮/其他投入；
    不看当前库存是否足够、不看现金是否足够，直接按预期缺口挂
  - 供给单：只挂本轮生产后的实际剩余盈余
  - 商品与土地同一订单簿；土地按 hex + 数量挂单，无 block
  - 未付货款形成普通债务；跨 hex 先走简单运力函数

M5 Social 事实回传
  - 经济回传实际温饱/缺口
  - Social 据此计算下一 tick 出生、死亡等

M9 PendingFamineFacts（或后续事实槽）
  - 只回传实际温饱/缺口，不复制自然需求账
```

> 待确认：债务清算在“生产轮之前”还是“市场轮开头”仍需与市场轮定义统一；旧口径是市场轮最前面，本文暂保持“市场轮最长”。

## 四、土地数据模型

### 4.1 形状

土地是不可生产、开局固定、和 hex 绑定的标量商品。建议用带 hex 键的库存行表示：

```text
LandHolding {
  hex: HexCoord
  owner: HouseholdId
  operator: HouseholdId
  quantityMilliMu: long
}
```

- 一个家户可以在多个 hex 持有土地；
- 每个 hex 的固定可耕地量由地图/地形枚举得到；
- `Σ_owner quantityMilliMu(hex, owner) == arableMilliMu(hex)`；
- 不允许凭空生产 LAND；不允许跨 hex 的同质数量合并；
- 土地不是普通 `HouseholdGoods` 的无地点键行，必须有 hex 维度。

### 4.2 市场与债务

- 土地市场订单：`(hex, side, quantityMilliMu, price/budget)`；
- 订单不带 block id；
- 买地/卖地可以任意数量成交；
- 债务抵地：从债务人的具体 hex 持有中扣数量，转给债权人；
- 0 价土地可以转移，但作为还债资产时价值为 0，债务本金不减少；
- 土地价格仍按市场区一个价（`landPrice` 是区级参考价），不是每个 hex 一个价；
- `landAcquiredThisRound` 用数量标记，下一轮清空，下一轮可正常生产。

## 五、生产方式成本与 Social 温饱接口

### 5.1 `naturalNeeds` 的边界

- 经济侧不再有独立的 `naturalNeeds`/`effectiveDemand` 需求表；
- Social 侧保留人口、温饱线和实际温饱统计接口；
- 每个家户配置一条 `satietyLine`（温饱线）；
- 生产方式读取本 tick `satietyLine`，计算该生产方式每 tick 的粮食消耗；
- Social 用实际温饱结果计算出生率、死亡率等，不把 `naturalNeeds` 再注入经济作为第二本账。

### 5.2 生产方式成本

标准 `grain_farm` 只保留一个生产方式，使用同一个 `grain` 商品：

```text
ProductionCostQuote {
  remainingSeedNeed:   未耕种面积 × 每亩种子量
  dailyFoodNeed:       本户温饱线对应的每日粮食消耗
  otherDailyInputNeed: 后续生产方式扩展，本批为空/暂不做
  expectedOutput:      按实际耕地/劳动/投入得出的产出
  expectedSurplus:     实际/理论产出 - 自身消费 - 必要投入
}
```

硬约束：

1. 已耕种面积不再产生种子需求；
2. 全部耕地耕种完 ⇒ `remainingSeedNeed = 0`；
3. 实际没有种子 ⇒ 本生产轮按实际可覆盖面积播种，剩余面积等下一市场轮买种再播；
4. 种子和日粮都是 grain，但不能用一个没有时间维度的 `productionCost` 直接相加；
5. M7 实际播种只扣实际播种部分；不能按 full planned capacity 一次性扣完；
6. 跨户不能共享种子/粮食；只有同一生产组织/同一 roster 的共享投入才允许。

### 5.3 劳动位置选择

- 自耕/经营位置与受雇位置进入同一个位置比较；
- 家户按单位劳动净收益选择位置；
- 受雇没有正收益 ⇒ 不占位，让位给收益更高的位置；
- 同 hex 有雇佣需求且后到户有剩余劳动，可以响应；
- 实际生产轮的 `ProductionRoster`/劳动回执由实际响应结果形成，不是创世预置。

### 5.4 收入归属

- 有地家户按该 hex 的土地数量获得对应耕地粮食；
- 无地雇农只获得雇佣者支付的货币工资；未付部分为普通债务；
- 不存在多户 share pool/shared revenue；
- 无租约/租地合同；无地户通过市场用债务买地，下一轮作为小农加入生产；
- 不再使用 product-share 作为跨户收入分配池。

## 六、当前代码冲突与新增问题

### P0

1. **同 hex 独立农场被错误合并为共享投入池**  
   `ProductionInputSettlement.rationContestedInputs` 把同一 hex、同一商品的多个独立家户需求合成池；A 户的粮可能给 B 户做种子。  
   土地和粮食都归具体家户；只有同一组织/roster 才能共享。

2. **M7 按 full planned capacity 一次性扣种子**  
   `drawCycleInputs`/`surveyInputDemands` 在 `progressDays==0` 时按计划规模扣料，M6 又在此之前用 `cycleInputUsed=0` 排劳动。  
   结果：播不了的地也先扣种子；农场在 M6 被判 `NO_INPUT`，劳动被分去别的活动。

3. **没有实际已耕种面积**  
   `ProductionProcess` 只有 `progressDays`/`cycleInputUsedMilli`，没有 `sownLandMilliMu`；`ProductionEfficiency` 只按累计投入/平均劳动算 scale，未以实际耕地为上限。  
   需要派生或显式状态，并进入 Codec/ChangeSet/roundtrip。

4. **`naturalNeeds` 删除后，M5/市场/购买力/缺口读口全部要改到生产方式成本**  
   `MarketRosterBook`、`MarketIntentBook`、`MarketPayChoice`、`HouseholdPurchasingPower`、`FxQuoteBook`、`ConsumptionSettlement`、`EconomyHouseholdGap` 等都要改；否则会留下第二本需求账或读不到需求。

### P1

5. **`MarketRosterBook.necessaryInputsOf` 按所有 unit、满计划规模预留**  
   不看 M3 选中位置、不看当前进度、不扣已扣种子；市场每轮重复预留整周期种子。

6. **`MarketIntentBook` 仍按库存差/现金预算裁需求**  
   `goodsOf`、`remainingBudget <= 0`、`maxSpend` 与“预期缺口直接挂需求单、不看实际支付能力”冲突。

7. **M3 意向按 actor 删除自动订单**  
   `MarketRoundRunner.replaceAutoCommodityOrdersForIntentActors` 删除同一 actor 的所有自动买卖单；应按 `(actor, commodity, side)` 合并/替换。

8. **非农生产方式抢农村劳动**  
   `ProductionRuntimeSeeder` 为农村 hex 建了 weave，标准小农业里 poor/middle 的 farm 被 `NO_INPUT` 后劳动去了织布；本批应只保留 `grain_farm` + 无业/必要占位，或显式禁用农村非农生产。

9. **固定 hired participant 只来自 displaced 户**  
   当前每个 hex 只给一个 landless/displaced 户发 `hired_laborer` 名册项，其他有剩余劳动的家户不能受雇；应改为同 hex 动态响应/位置选择。

10. **土地 block 模型与新裁定冲突**  
    `OwnershipStake.landBlockIdOf`、`AssetShareId`、`MarketLandOrder`、`DebtFirstSettlement` 整块转移、`landAcquiredThisRound` block set 都必须改成 `(hex, quantity)` 标量模型。

11. **0 价土地的债务语义未定义**  
    0 价可转移，但债务本金不变；当前 `DebtFirstSettlement` 对 0 价值块仍会执行转移，需明确“转移不等于抵债”。

12. **运力为零**  
    `MERCHANT_CAPACITY_HOUSEHOLD` 的 `capacityMilli` 全 0；跨 hex 市场实际瘫痪。先加简单运力函数 + 象征性价格，不新增生产方式。

13. **创世预设生产组织**  
    `Rural32HexWorld`/`ProductionRuntimeSeeder` 当前在 tick0 预置 160 个 farm unit/roster；按“tick0 没有生产方式正常”的口径，应把定义与已选中生产实例分开。

14. **无地户拿到土地后没有生产组织**  
    土地在 landless 名下，但其 `participationPerMille=0`、没有实际劳动/unit；下一轮虽可用，但没有组织者/劳动时会荒置。需要明确获得土地后如何作为小农加入生产。

## 七、新的裁定/待确认

以下是把用户原话落成设计后仍需要继续确认的边界；在此之前不应自行补默认：

1. **温饱线单位**：单户温饱线是“每户每 tick 粮食数”，还是“每户每人每天粮食数 × 人口”？
2. **土地收入分配**：同 hex 多户持有土地时，产出按土地数量分配，但种子、日粮和雇工工资由谁先承担/如何按土地分摊？
3. **雇农工资的雇主**：多户土地所有者共同在一个 hex 生产时，谁是雇佣者/工资债务人？是具体组织者还是按土地份额分摊？
4. **生产轮与市场轮之间的债务时点**：债先于市场，但生产轮在前时，M2 债务是在生产前还是市场前？
5. **温饱线配置的归属**：Social 只提供单户配置和实际温饱结果，还是也提供“按生产方式的日粮曲线”？
6. **标准小农业测试范围**：是否先移除农村 weave/craft/trade，只保留 `grain_farm` + 无业 + 地方政府？

## 八、建议实施顺序

1. **重写目标运行序列**：生产轮 → 工资 → 市场；naturalNeeds 删除；温饱线接口保留。

### 效率公式的正确写法

用户文字里的 `b=b-(a/u)*(w/(a*v))` 与“满效率应为100%”矛盾。按示例的 5% 损失意图，正确实现应为：

```text
efficiency_i = min(1, w_i / (a_i * v))
b = 1 - Σ_i (a_i / u) * (1 - efficiency_i)
```

其中：

- `a_i`：第 i 个家户在该 hex 拥有的土地；
- `v`：当前生产方式每单位土地每 tick 需要的劳动；
- `w_i`：最终落到该家户土地上的实际劳动（自耕 + 收到的雇工劳动）；
- `u`：该 hex 总农业土地；
- `efficiency_i` 封顶 1；
- 若全部满劳动，`b=1`；若某户 `w=0`，损失 `a_i/u`。

用户示例：

```text
u=1000, a=100, v=1, w=50
efficiency = 50/100 = 0.5
b = 1 - (100/1000)*(1 - 0.5) = 0.95
```

即该日 hex 总效率95%。

   毛产按土地份额分给 owner 后，owner 再支付工资；如果 owner 还没拿到毛产，工资债的记账时点是分配后立即，还是下一 tick？

   一个家户既有自耕土地又受雇时，日粮只应扣一次；需要明确是按户扣、按生产位置扣，还是按实际劳动时间分摊后只扣一次。

### 当前经济系统怎么处理 NaturalNeed（调查）

当前是“多张表 + 多入口”：

1. **Social 侧计算**  
   `PopulationEconomyTimeParticipant.naturalNeedsOf(SocialData, day)`（app 侧）逐户调用 `social.householdNaturalNeeds(household, day, clock)`，生成逐户逐商品需求，再 `stepper.updateNaturalNeeds(...)` 注入经济。

2. **经济状态**  
   `PopulationWritebackSettlement.applyNaturalNeedsInto` 是 `HouseholdEconomy.naturalNeeds` 的唯一写点；家户行保存一份当天需求。

3. **M5 消费**  
   `ConsumptionSettlement.consumeOneHousehold` 读 `current.naturalNeeds()`，从家户库存扣 grain/cloth；缺口写入 `unmetNeed`/`deficitToday`，并累加 `cycleNaturalNeedMilli`。

4. **市场预留/购买力**  
   `MarketRosterBook.householdLifeReserveOf` 和 `MarketIntentBook` 使用 `naturalNeeds × 5 天` 形成买卖保留与消费缺口；`MarketPayChoice`、`HouseholdPurchasingPower`、`FxQuoteBook` 也用它算“付清需求”的购买力。

5. **生存事实又另起一套**  
   `SocialSurvivalFacts.forNextTick(SocialData, nextTick)` 又直接调用 `social.householdNaturalNeeds`，生成 `SurvivalSocialFacts` 给 `SurvivalOutlook`/劳动分配，不读 `HouseholdEconomy.naturalNeeds`。

6. **读口/GUI/危机**  
   `HouseholdQueryService`、`ApiViews`、`CrisisMonitor`、`HouseholdQueryService` 等又各自读 `HouseholdEconomy.naturalNeeds` 或 `cycleNaturalNeedMilli`。

⇒ 所以当前不是“一张需求表”，而是至少：
- Social 的 `householdNaturalNeeds`；
- app 注入的 `naturalNeeds`；
- `HouseholdEconomy.naturalNeeds`；
- `SocialSurvivalFacts` 的 `NextTickSubsistenceNeed`；
- 市场 5 日 reserve 的派生量；
- GUI/危机读口。

这正是你 5.5 说的“从这边拉个表、那边拉个表”。

### 目标：单一口径 `DailyDemandBill`

建议形状：

```text
DailyDemandBill {
  day
  household
  lines: [
    { commodity, quantity, source: BASE_SUBSISTENCE },
    { commodity, quantity, source: PRODUCTION_DAILY_EXTRA },
    ...
  ]
  totalInventoryDeduction
  marketPurchaseNeed
  unmet/gap facts
}
```

- `BASE_SUBSISTENCE`：Social 温饱线算出的基础日需求；
- `PRODUCTION_DAILY_EXTRA`：当前生产方式的额外单日消耗（目前只做少量增加，例如干活多耗一点粮）；
- 种子是**周期/播种日**成本，不放进每日需求账单；
- 市场、M5、购买力、缺口、GUI、危机都只读这一张账单；
- Social 只提供温饱线/人口/实际温饱结果，不再让 economy 从多处拉需求表。

### 这件事的实现边界

1. **旧 `naturalNeeds` 字段删除**  
   不能保留 `HouseholdEconomy.naturalNeeds` 和 `DailyDemandBill` 两份；Alpha 不兼容旧档，Codec/ChangeSet 同步改。

2. **`cycleNaturalNeedMilli` 也要重定义**  
   当前它是“逐日累加 naturalNeeds[grain]”；新模型应改为“逐日累加 DailyDemandBill 的 base+production extra（或分项累加）”，并写清商品维度。

3. **`SocialSurvivalFacts` 改为读同一账单**  
   不能再让 app 从 Social 重新生成第二份需求表；它可以携带劳动预算/温饱线/实际温饱，但需求行必须来自同一 `DailyDemandBill`。

4. **市场 5 日窗口**  
   如果市场仍需要 5 日前瞻，应把 `DailyDemandBill × 5` 的派生明确为市场读法，而不是另造一张 naturalNeeds 表。

5. **GUI/查询/危机读口**  
   所有读口改成读 DailyDemandBill 或其派生只读视图，不能继续读 `HouseholdEconomy.naturalNeeds`。

### 仍然需要确认

1. **单日需求账单的写入者**  
   是 production 计算 `DailyDemandBill`、economy 只读？还是 app/Social 汇总后 economy 持有唯一副本？按模块边界，我倾向 production 生成生产额外项，Social 提供 base 温饱线，app 组装成唯一账单，economy 持有当前 tick 的唯一副本。

2. **生产方式额外单日扣除的“较小增加”具体量**  
   是按出工劳动比例增加，还是每个生产位置固定增加？需要给一个工程默认。

3. **日粮与雇工日粮**  
   `DailyDemandBill` 是家户一张，雇工位置只是把其日粮作为该户的 production extra 行；不能让 worker 位置和自耕位置各生成一张独立日粮表，否则重复扣。

4. **效率公式的跨日汇总（已收口）**  
   用户 2026-10-19 更正 7.2 为“后者吧，看着靠谱一些”：采用 `B_cycle = Σ_d (u × B_day_d) / (u × cycleDays)`。u 固定时等价于每日 `B_day` 的算术平均，但实现保留按土地量×天数累计的形式。
