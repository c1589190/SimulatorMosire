## 〇、根因：v1 把两件不同的事混进了同一处

| 混进代码里的东西 | 它其实是什么 | 后果 |
|---|---|---|
| `outputPerUnit = 7`、`PRODUCTION_CONSUMPTION_PER_MILLE = 150`、`CLASS_SHARE_PER_MILLE`… | **可调的输入**（参数） | 散在 Java 常量里 ⇒ GM 无法调、场景无法校准、改一个数要重编译 |

本版的口径一句话：**先把"数"做出来，别急着做"判"。**

## 一、v1 的三个已确认故障（本版要修的根因）

### 1.1 参数与人口量级不自洽（唯一会改变"用户点了推进之后看到什么"的错误）

v1 口径：每格 `MU_PER_HEX = 1000`（亩）× `GRAIN_OUTPUT_PER_MU = 7`（粮/亩），每人每周期 10 粮。
⇒ 单格承载力 = `1000 × 7 × 0.85 ÷ 10 ≈ 595 人/格`。

而人口取自冻结场景（`config/worldgen/v17levant-nations.json`，与 `social.SetPopulation` 同源）：

| 国家 | 格数 | 人口 | 人/格 | 周期需粮 | 周期净产 | 自给率 |
|---|---|---|---|---|---|---|
| 德意志第二帝国 | 430 | 6,230,000 | 14,488 | 62,300,000 | 2,558,500 | **4.1%** |
| 奥斯特马克侯国 | 138 | 3,070,000 | 22,246 | 30,700,000 | 821,100 | **2.7%** |
| 霍赫兰伯国 | 231 | 2,530,000 | 10,952 | 25,300,000 | 1,374,450 | **5.4%** |
| **合计** | **799** | **11,830,000** | **14,806** | **118,300,000** | **4,754,050** | **4.0%** |

⇒ **超载约 25 倍。** 一次完整收获（净 5,950 粮/格）只够该格吃 **5 天**。v1 spec §十 验收判据 3「库存曲线呈现青黄不接 → 收获」**在数学上不可能出现**。

### 1.1.1 量纲标定（★ 本版的必要前置；写实现计划时才发现 v1 spec §九 V2 漏了这条）

**约束式**（每格每周期，全部用代码里的真实常量，含 15% 生产消耗）：

```
每格每周期需粮 = 人口 × 83 毫粮/人·日 × cycleDays ÷ 1000
              = 14,806 × 83 × 120 ÷ 1000 = 147,468 粮
每格每周期净产 = muPerHex × 亩产 × (1 − 饲料率 − 折旧率)
              = muPerHex × 亩产 × 0.85
⇒ 自给条件：muPerHex × 亩产 ≥ 147,468 ÷ 0.85 = 173,492
```

**两个旋钮，各取一即可**（★ **待裁**，见 §10.3）：

| 方案 | `muPerHex`（每格亩数） | 亩产（粮/亩） | 两个数是否落在真实区间 | 代价 |
|---|---|---|---|---|
| **A（推荐）** | **1,000 → 3,100**（≈2.07 km²/格） | 保持 **67** | **都在**（前现代小麦亩产 ≈ 67 kg/亩；人口密度 ≈ 7,150 人/km²…仍偏高但可控） | 动"地图经济尺度"这个本来任意的数 |
| **B** | 保持 **1,000** | **7 → 210** | 亩产**超出**前现代区间（≈现代农业水平） | 只动一个纯假设值；但"中世纪亩产 210 公斤"政治上不诚实 |
| C | 1,000 → 2,000 | 7 → 90 | 两者皆在真实区间边缘 | 两个数都要动，审计面更大 |

★ **取 120% 自给**（不是刚好 100%）的理由：农业还要养活**城市人口**（手工业现在产 0，见 §八.2 的 A 条）与**军队**，并有存储损耗。A 案的 3,100 亩/格即按 120% 反推。
★ `muPerHex` **与地图无关**：`HexCell` 只存 height，格面积是**纯经济假设**，改它不牵动 map。

### 1.2 地形产能两处真相

- `simos-map` 的 `TerrainType` 已有 `int food`（粮食产能）字段：平原 3 / 低丘 2 / 平缓高原 1 / 沙漠 0 / 山地 0 / 海洋 0，**六档**（`TerrainCatalog.java:48-70`）。
- `simos-app` 的 `EconomySeeder.terrainCoefPerMille`（`:282-289`）另写一份**两档**表（平原 1.0 / 低丘 0.6），其余地形 **fail-closed 抛**。

⇒ 真相在 `map`、且比 economy 那份细。而且 fail-closed 是**潜在硬失败**：`surplusRatePerTerrain` 给 `plateau 0.3 / mountains 0.1 / desert 0.02` 都分配农村人口，一旦地形直方图变化或新增国家，`simos.worldgen.initialize` 会整批 BAD_REQUEST（人口+城市+军队一起回滚）。
（当前三国的 `terrainHistogram` 恰好只有 plains/low_hills 且合计正好 430/138/231 ⇒ **现在不会崩**。这是潜在风险，不是既成故障。）

`TerrainType` 另有 `int gold`（金/铜）与 `int stone`（石/铁）两个产能字段，同样**零读取点** —— 这是 v1 spec §十 里"霍赫兰铁矿/铜矿格加矿业"（84 格）现成的依据。

### 1.3 判断结果被实现成机制

`EconomySettlement.applyFamine`（`:425-445`）+ `FAMINE_MORTALITY_PER_MILLE`（致死率，`:95`，现 200‰）出自 commit `675f99e`（用户 2026-09-25 点名）。按本版口径它属于"判断条件与结果"，而支撑它的数学基础缺失。

**处置（取代声明）**：`applyFamine` 与 `FAMINE_MORTALITY_PER_MILLE` **改为"机制保留、默认不生效"** ——
- `FlowRow.unmetNeed`（未满足需求，毫粮累计）的逐日累计与读口暴露**保留并做实**；
- 致死率 `FAMINE_MORTALITY_PER_MILLE` **默认 `0`‰（即不生效）**，人口不因缺口减少；
- 致死率本身**做成 GM 可调参数**（见 §四 参数目录，制度层）。

本条**取代** 2026-09-25 的"饿死惩罚"点名（commit `675f99e`）的实现口径，依据用户同日两句话：
「可以先不做什么饿死人系统、青黄不接系统」+「我认为全都应该算GM可以改的行为预设——GM是不是老傻子是GM的事，**项目代码应当是自由的**」。
★ 两句并读：**"先不做" = 默认不生效；信条十二要求的是"旋钮要在"**。切勿读成"删掉机制"。

## 二、口径：什么算"数学基础"，什么算"判断结果"

| 算**数**（本版**算出来**） | 算**判**（本版**不预设值**，但**做成 GM 可调的旋钮**，默认值保守） |
|---|---|
| 需求 = 人口 × 口粮系数 | 饿了多久算"饥荒"（阈值参数，默认不触发） |
| 供给 = 瓶颈 `min`（土地 / 劳动 / 种子） | 饿死多少人（致死率参数，**默认 0‰**） |
| 缺口 = 需求 − 实得（逐日累计，**只记数**） | 阶层流动（中农 → 贫农）的判据与阈值 |
| 种子粮在库存里、可被吃、吃了下期减产 | 产业转换（农业 → 工坊）的判据与阈值 |
| 地租 / 利息 / 留种的**计量** | `effectiveDemand`（有效需求）的"支付力"判据 |
| 守恒（粮 / 钱 / 人口） | 地租上限 / 最低工资 / 禁令的效果 |
| 全部可观测（GUI / MCP 读得到） | 债务的**偿还**行为（计息属"数"，本版做） |

★ **口径（信条二 + 信条十二并读，2026-09-25 裁定）**：

1. **判的"结论值"不预设** —— 不替 GM 定"缺口到 45.8% 就该死 20%"这种数；
2. **判的"机制与旋钮"要有** —— 参数位、默认值、可调；**代码不替 GM 做价值判断**；
3. **默认值可取保守 / 关闭**，但**不许写死**。

★ 判据：任何新增逻辑都要能回答"它是**数**，还是一个**可调预设**"。两者都不是的，不进本版。

★ 因此本版**不划"这算数还是算判"的边界**（原先由我划的那条边界已被推翻）：**凡"行为"一律做成预设**，
由 GM 决定取什么值。例：播种该不该先于吃饭扣种、放贷方要不要留口粮 —— 各自是一个参数（默认值保守），
**不是**由代码选一个"聪明的"行为钉死。

## 三、产能模型（取代 v1 的 `outputPerUnit` 常量口径）

### 3.1 三路瓶颈

```
基础可耕地 baseArableMu  = 每格基准亩数 × 地形可耕系数        ← map（地形）
平均实际劳动 avgLaborMilli = Σ(本周期逐日实际劳动) ÷ cycleDays  ← social（人口→有效劳动）
劳动可经营 laborMu       = avgLaborMilli × 每标准劳动可种亩数  ← 技术参数
种子可支撑 seedMu        = 已备种子 ÷ 每亩需种                ← economy 的库存（播种日现扣）
实际投入 plantedMu       = min(baseArableMu, laborMu, seedMu)  ← 瓶颈在最短那块
基础单产 baseYieldPerMu  = 地形 food 系数                      ← map
毛产出 grossOutput       = plantedMu × baseYieldPerMu
```

★ **耕牛不做**（用户 2026-09-25：「耕牛系统觉得复杂现阶段就别做」）。故 `AssetKind.CATTLE/TOOL/WORKSHOP/MACHINE/SHIP` v1 **保持声明但不启用**——与今天 `dailyInputPerUnit` 的状态相同（字段在、零读取点）。这点必须写进代码注释，免得后来人以为它们已经生效。

★ **地形系数读 `TerrainType.food`**，不再自建表。这解决了 §1.2 的两处真相，也顺带解除 fail-closed 的潜在硬失败（`food = 0` 的地形自然得到 0 可耕地，不需要抛）。

### 3.2 播种时序（一个商品的口径要求它必须有时序）

**种子粮与口粮是同一个商品 `grain`，不设 `seed`。** 理由（用户 2026-09-25「不要把吃的粮食和种子粮分开算」）：在政治经济学里，生产资料 / 生活资料的区分是**同一物在循环里承担的职能**，不是物的物理属性。做成两个商品 id 等于把职能差别固化成物的差别，而且会立刻造出两个假问题（"剩的种子能不能吃""吃的粮能不能播种"）。

**代价是必须有播种时序，否则种子永远保不住**（每天先吃饭会把种子吃光 ⇒ 缺粮格永远播不了种 ⇒ 产量永久归零）。故：

```
周期第 1 天（progressDays == 0）：
    先扣应投种子 → 扣不动就按扣得动的比例缩减 plantedMu（经 seedMu 进瓶颈）
    剩下的才是本周期可吃的
周期第 2..cycleDays-1 天：正常日结算（消费 / 投入 / 进度）
周期第 cycleDays 天：收获
```

★ **种子的优先性来自"时点"，不来自"种子神圣不可吃"的规定**。播种日就是那天，那天之前吃掉的已经吃掉了。于是「冬春把缸吃空 ⇒ 播种日扣不到种 ⇒ 投入面积缩 ⇒ 减产 ⇒ 下一年更缺」这条链条**不需要任何判断条件**，它就是时序加数字。

★ 由此 **`INITIAL_RATION_DAYS_BY_CLASS`（阶层差异化储备天数）保留**：它是初始条件、是个数，不是判断结果。

★ **但"播种日先于消费扣种"这个次序本身也是可调预设**（信条十二：凡行为一律做成预设）：
参数 `plantingDrawsBeforeConsumption`（播种是否先于当日消费扣种，布尔），**默认 `true`**（保守：保证种子有意愿时能留住）。
取 `false` 即"吃饭优先、种子看运气"——那是 GM 的选择，不是代码该替他做的判断。
★ 参数化**不许改变流程形状**：无论取真取假，播种日这个**步骤**都在（见 §5.3 的"留空步"口径），只是扣减次序不同。

### 3.3 一次性投入的槽位（新增一格）

v1 的 `Industry.dailyInputPerUnit`（每单位生产资料**每日**原料需求）**语义不适配种子**（种子是播种日一次性扣完，不是每日）。故新增：

```java
Map<AssetKind, Long> cycleInputPerUnit   // 每单位生产资料**每周期一次性**投入
```

`dailyInputPerUnit` 保留（将来手工业/矿业的每日原料要用）。两个字段并存，语义各自清楚。

★ **`cycleInputPerUnit` 的 v1 键是 `LAND`**（每亩需种多少）。`AssetKind` 六种里 v1 实际只有 `LAND` 会被读到。

### 3.4 生产消耗：从常数拆成三项

v1 的 `PRODUCTION_CONSUMPTION_PER_MILLE = 150`（15%）是**永远拿得出来的常数**。v2 拆成三个独立参数：

| 项 | 性质 | 去处 |
|---|---|---|
| 留种 | **已由 §3.2 播种日扣除取代**，不再从收获里扣 | — |
| 饲料 | 参数（千分比） | 收获时扣，明文入 `FlowRow.consumed` |
| 折旧（农具） | 参数（千分比） | 同上 |

★ 留种**不再作为收获时的扣除项**——它在下一周期第 1 天以 `cycleInputPerUnit` 的形式扣。这是本版最重要的口径修正：留种从"收获的固定百分比"变成"播种日的实际投入"。

## 四、参数目录（ParameterCatalog）

### 4.1 按"决定者"分三层，不是按模块分

| 层 | 本质 | **决定者** | 归属 | 例子 |
|---|---|---|---|---|
| **物理层** | 世界如何运作 | **没有主体** | 地形产能归 `map`（`TerrainType.food`）；其余住 `economy` 的 `worldParams` 子表（见 §4.1.1） | 地形产能、口粮系数、每标准劳动可种亩数、饲料率、折旧率 |
| **制度层** | 社会如何组织 | **生产关系双方** | `economy` | `AllocationRule.Split` 权重、租佃习惯、每亩需种 |
| **政治层** | 国家强制什么 | **国家机器** | `government`（★ 尚未存在） | 税率、关税、最低工资、地租上限、出口禁令 |

★ **层不是"存放位置"，是"约束叠加"**。反例：**地租** = `min(合同地租, 政府上限)` —— 制度层与政治层合成，这个数不存在于任何单独一层。

★ **"逐层"在两层的含义不同，不可混**：
- **政治层**的逐层 = **权力层级**（国家 → 下级行政单位）；
- **物理层**的逐层 = **空间层级**（全球 → 格）。
⇒ **"某国覆盖自己的亩产"是语义错误**（国家不能决定自己土地的地力）。技术进步的**正确建模是生产资料存量变化**（更多农具/机器），不是覆盖物理常数。

### 4.1.1 物理层参数落在哪个切片（★ 本版自审补的洞）

物理层"没有主体"，但**项目里所有状态都必须住在某个切片里**（`SimulationState.modules`）——"无主体"不等于"无处安放"。定案：

- **地形产能**（`TerrainType.food` / `gold` / `stone`）**已经是 `map` 的数据**，原地不动、原地读。这是它本来的归属（地形是地图的事实）。
- **其余物理层参数**（口粮系数、每标准劳动可种亩数、饲料率、折旧率）**住 `economy` 切片的 `worldParams`（世界参数）子表**。

理由：用它们的**只有** economy 的结算公式；为它们单开一个切片，收益不足以抵消成本（新切片 = 新 codec + 新 ChangeSet + 新往返测试 + 新 enforcer 条目 + Shell 注册）。

★ **但它必须在语义上与"经济主体的数据"分开**：
- `worldParams` 是**世界参数**，不是任何主体（阶层/政府）的所有物；
- 参数目录里它归**物理层**分区，不与制度层的分配权重混在一张表；
- **不许**出现"经济切片里的库存/货币"那类主体语义混进 `worldParams`。

★ `government` 切片落地后，**政治层参数住 `government`**，不动 `worldParams` 的边界。

### 4.2 多层作用域，就近优先

作用域链：`全局 → 国家 → 格/区域 → 产业 → 阶层`。查找规则：**从最具体的一层往上找，第一个命中就用它**。

★ 键用项目既有的 `Address`（地址）+ `canonical()`（规范形式）——每格、每国、每产业都已有稳定规范地址，覆盖表的键即 **"参数名 + 作用域地址"**。
★ 好处：① 加层不改结构；② "逐层"就是地址前缀逐级放宽，不是多套逻辑；③ **能反查来源**（GM 面板可显示"此值由霍赫兰层覆盖，全局默认 10%"）。

**v1 落地范围：全局 + 国家两层**，但按五层形状设计。

### 4.3 每个参数自带"最小作用域"

由参数性质决定下界，**API 层据此自动拒绝在更粗的层写它**（不靠人自觉）：

| 参数 | 最小作用域 | 理由 |
|---|---|---|
| `taxRate`（税率） | **国家** | 征税主体是国家，不存在"全世界税率" |
| `outputPerUnit` / `baseYield`（亩产） | 全局 | 自然规律 |
| `DAILY_GRAIN_MILLI_PER_PERSON`（口粮系数） | 全局 | 生理规律 |

★ 想设"全球税率"⇒ 直接拒，理由可读。

### 4.4 归属：值各自拥有 + 统一目录

- 参数**值**住在各自切片（铁律 3 不破：税的参数属 `government`、亩产属 `economy`）；
- 每个切片**声明一份参数清单**（名字 / 单位 / 取值范围 / 最小作用域 / 说明）；
- `ParameterCatalog`（参数目录）把它们聚起来给 GM，**按 §4.1 的三层分区**，不是一张平表；
- 改参数走各自切片的命令，**改参数的 tick 即一条 revision**。

★ **分岔管理**（用户 2026-09-25 裁定）：参数**不能是配置文件或全局变量**，必须是被 revision 带着走的**切片状态**。这样两条分支各自带自己的参数值；存在 `config/` 里则两分支共用一份，分岔管理失效。

### 4.5 生效语义：立即生效，只管未来

- 改完那一刻起、之后的结算用新值；**已结算过的日子一个数都不改**。
- 理由有个技术事实：多数参数**不是每天读**，而在特定时点读一次（`outputPerUnit` 只在收获日读、播种参数只在播种日读）。故"立即生效"对多数参数天然等于"下一个使用点生效"，省掉"参数快照"这一整块复杂度。
- **v1 不做回溯重算**（不存每次结算的参数快照）。

★ **守卫**：目录里"声明了的参数"必须有测试钉住**真的能读、真的能改**——否则会出现"面板上有、改了没用"的假参数（本仓最忌的那一族）。

### 4.6 政治层：不建切片，只留接口

`government` 切片**v1 不建**（用户 2026-09-25：「当前已有模块要为后续政府模块的政策调控预留好接口」）。目录的政治层分区**留空位**并标注"由 `government` 切片登记"。索取源的注册位见 §五。

### 4.7 ★ 两类参数：覆盖式 vs 实例式（不要把两者混成一个机制）

§4.2 的作用域链只对**第一类**成立。参数分两类，机制不同：

| | **覆盖式参数** | **实例式参数** |
|---|---|---|
| 形状 | 全局默认值 + 逐层覆盖（一张覆盖表） | 本来就**逐实例**不同，住在实例里 |
| 典型 | 口粮系数、饲料率、折旧率、每亩需种 | `AllocationRule` 权重、`cycleDays`、`baseYield`、`cycleInputPerUnit` |
| 归属层 | 多为**物理层**（世界规律） | 多为**制度层**（合同/习惯） | 
| 住在哪 | 参数目录（新组件） | `Industry` / `ClassSlot` 实例内（**已有形状，不动**） |
| GM 改它 | 写覆盖表一行 | **对匹配作用域的实例批量写**（一条命令改多实例，仍是一条 revision） |

★ **为什么不能统一成一个机制**：分配权重 `Split(700, 300)` 逐产业不同是**本质**（同一国内不同产业有不同制度），把它拉平成"全局默认 + 覆盖"会立刻要求给每个产业各写一行覆盖——那比住在实例里更啰嗦，而且丢掉了"这一格的这个产业就是这个制度"这个事实。

★ **这条区分与 §4.1 的三层是同一件事的两面**：物理层天然覆盖式（规律不分主体），制度层天然实例式（合同逐份签）。政治层（税率）是覆盖式、按国家——因为**税法对一个国家是统一的**。

★ 落到 GM 体验：两类参数在面板上都出现，但操作不同——覆盖式是"改一个数"，实例式是"对一批对象批量改"，**批量改的结果必须能回读**（"我刚把 430 格的分配权重改成 600/400"要能查证是哪些格）。

## 五、索取源协议（取代"给政府留两个空步"）

v1 spec §四 的结算顺序里有两步是政府的（每日第 7 步征税、周期第 2 步产出税），而 economy 的代码里**这两步整段缺席**。若将来插入就得**重排顺序**，顺序一改则所有历史数值口径跟着变。

★ **但"给政府留两个空步"太窄**——它不是接口，是给一个模块开的后门。军队临时征粮、决策人下令赈济、将来市场收运脚费，全是"从经济里往外拿东西"。

### 5.1 协议（与 `Facet` / `TimeParticipant` 同族，这是第三次用该模式）

住 **`simos-util/spi`**（共同上游：谁都能看见，但没人被反向依赖）。**形状照抄既有协议族**，不另造类型：

```java
public interface SurplusClaimSource {   // ★ 不叫 ClaimSource：ledger 已有 model.Claim（债权），撞名
                                        // 本协议是 simos-util/spi 的第 13 个协议（既有 12 个见该包）
  String sourceId();                    // 稳定 id —— 决议排序用，保证可复现

  Set<String> reads();                  // ★ 与 TimeParticipant 同款：canonical 地址，供冲突检测
  Set<String> writes();                 //   （v1 spec §九 的读写集检查对每个 namespace 一视同仁）

  List<SurplusClaim> claimsIn(ClaimContext ctx);        // ① 提出索取（纯读自己的基态）

  Map<String, ChangeSet> settle(ClaimResolution res);   // ② 按实际满足量落回**自己的切片**
                                                        //    namespace → ChangeSet（照 WorldTimeProposal.moduleChanges 的类型）
                                                        //    ★ 无事也交**不变变更集**，不许交空
}

public record SurplusClaim(             // ★ 不叫 Claim：见上
    String  claimantId,        // 索取主体（政府 / 某支部队 / 地主阶层…）—— 稳定 ID
    String  commodityId,       // 商品（粮）
    long    amount,            // 数量
    ClaimPhase phase,          // 在哪一步提（对齐 v1 spec §四 的顺序）
    int     priorityPerMille,  // 优先序（千分比）
    boolean mandatory)         // 强制（税 / 军队征粮）还是契约（租 / 利息 / 工资）
```

★ **三处照抄既有形状、不许另造**（`AGENT.md` 信条"先复用已有能力"）：
1. per-module 变更的类型就是 **`ChangeSet`**（`io.mosire.simos.util.state.ChangeSet`），容器是 `Map<String, ChangeSet>` —— 即 [`WorldTimeProposal.java`](../../../simos-util/src/main/java/io/mosire/simos/util/spi/WorldTimeProposal.java) 第 2 个组件的类型。不要自造 `ModuleChange`。
2. **不许用 `Optional.empty()` 表示"我没变更"** —— `WorldTimeProposal` 的构造期明令：**空提案是装配错误**，"本日无事"应交**不变变更集**（`Unchanged` 分量），否则"这一参与者是否真的参与了本次推进"会从事件里彻底消失。
3. **必须声明 `reads` / `writes`**（canonical 地址）—— 既有 `TimeParticipant` 就是这么做的，冲突检测用它。

★ **必须是双向的**：① 只提索取不够——东西得有地方落。而 `economy` 是纯函数、**不能写别人的切片**（铁律 3）。故 ② `settle(ClaimResolution)` 让索取源**按实际满足量产出自己切片的变更集**，该变更集与 `economy` 的变更集一起进**同一份 `WorldTimeProposal`**（多切片提案），一条 revision 原子提交。

★ **这就是"逐层暴露给下一个模块的可调整自定义影响接口"的完整形态**：提索取 → 统一决议 → 落回自己。`economy` 全程不知道对方是政府、军队还是市场，它只认协议。

### 5.2 决议规则（确定性、可复现）

- 同一 `phase` 内按 `priorityPerMille` **降序**；
- 同优先级按 `claimantId` **字典序**（与既有的债务 id / 槽位 id 排序同一套做法）；
- 依次从该格该阶层的库存里扣；**扣不动就记欠**（欠税 / 欠薪 / 欠租），**不凭空造粮**。

### 5.3 注册与"空步"的落地

| 模块 | 提什么 | v1 |
|---|---|---|
| `economy` 自己 | 地租、利息、留种 | **做**（协议的第一个真实 provider） |
| `government` | 产出税、商品税、关税 | 留位 |
| `unit` | 征粮、就地补给、行军消耗 | 留位 |
| `sd` | 赈济、禁令、上限 | 留位（这类是**改规则**，走参数目录，不走索取） |

★ 结算流程里 **phase 作为显式步骤保留**，内容从"政府征税"泛化为"**问所有已注册的索取源**"。将来是**填空**，不是**改序**。
★ 顺带明确 `FlowRow.taxPaid`（已纳税额，现恒 0）的含义：**它是本协议的槽**，不是待删字段。

## 七、债务（v1 借贷模型的两个问题）

### 7.1 借贷规则（问题 2.1）

v1 的三处（`EconomySettlement.java:296-344`）：

| 现状 | 问题 | v2 处置 |
|---|---|---|
| `lent = min(remaining, available)`（`:320`），`available` = 放贷行**消费后的全部库存** | **放贷方不留口粮**：地主一次把 250 天存粮全借出去，次日自己变成缺口行 ⇒ 设计意图（"地主最厚 = 同格主要债权人"）被反转成"地主先破产" | **做成制度层参数** `lenderSubsistenceReservePerMille`（放贷方保留口粮的千分比，相对本周期自需），作用域 全局→国家→格/产业。**默认值待定**（建议 1000‰ = 保留全周期口粮，即不贷出口粮；`0` = 全借出，即 v1 现状）。**不由代码钉死。** |
| 任何缺口行都建 `Debt` | **无支付力判据**（v1 spec §四 第 8 步要求"库存不足**且有支付力**"） | ★ **属"判断结果"，本版不做**。`effectiveDemand` 保留并恒 0，留位 |
| `ratePerMillePerCycle = 20` 写进去了，但计息/偿还一行都没有，`FlowRow.interestDue/repaid` 恒 0 | 账面记成"债务"，语义是**无限量无偿赈济** | **计息做**（纯数学：本金 × 利率 → 并入本金或记应付款）；**偿还行为留位**（需"有粮才还"的判断） |

★ 注释与代码相反的一处一并修：`:296` 注释说放贷方"可取**当日盈余**"，实现取的是**全部库存**。

### 7.2 债务表无界增长（问题 2.2）

v1 每个缺粮日、每个缺口行各建一条 `Debt`（id = `debt-<day>-<seq>`，`:322`），**永不偿还**。三国 799 格 × 4 槽位，缺口持续时每天新增约 3.2k 条 ⇒ 一年约 117 万条**永久留在 checkpoint 里**，与 v1 spec 核心原则"复杂度不随人口线性增长"相悖。

**v2 处置：按 (债权人, 债务人, 商品) 聚合 + 按周期关账。**
- 同一对债权债务人在**同一周期内**的多次借入**累加到同一条 `Debt`**（本金递增），不再逐日新建；
- 新周期开新条（保留"哪一周期借的"这一信息，供 §五 的到期/计息用）；
- ⇒ 债务条数上界从 `O(天数 × 格子)` 降到 `O(周期数 × 格子 × 债权人对数)`。

★ 这会改 `Debt` 的语义（从"一笔借据"变成"一周期内一对主体间的往来"），牵动 codec、ChangeSet、往返测试 ⇒ 单列一个增量（§九 R3）。

## 八、不变量与守恒（可构造期判的，落成测试）

1. **`0 ≤ participationPerMille ≤ slot.laborParticipationPerMille ≤ 1000`** —— v1 只守了两头，**中间那条无人守**（`ClassRow.java:61` 只判 `[0,1000]`；`EconomyData.requireSlotExists`（`:119-133`）拿到 slot 后只 `return`，没比这一对）。`EconomyData` 同时持有 industries 与 classes，**构造期完全可判**。后果：超上限投入率安静入库 ⇒ 劳动投入总量、瓶颈、按劳动权重的分配全被悄悄放大，且账面看不出来（不凭空造粮，但凭空造劳动）。
2. **引用完整性补两侧** —— `EconomyData.java:92-99` 的 debts 循环**只查 null**：`Debt.debtor/creditor` 可指向不存在的 `ClassKey`；`ClassRow.debts`（`List<DebtId>`）里的 id 可指向不存在的债务。两张表都在手，构造期可判。
3. **`progressDays == cycleDays` 是合法值却会炸** —— `Industry.java:80` 允许 `progressDays ∈ [0, cycleDays]`（闭区间），而 `EconomySettlement.java:187-190` 用 `progressed == cycleDays` 判收获、否则 `nextProgress = progressed` ⇒ 下一天构造出 `cycleDays + 1` 而**抛 IAE，整条推进 revision 失败**。当前 seeder 恒写 0 故未暴露，任何 `economy.Seed` 载荷或导入路径都能触发。
   ⇒ **定案：保留 `Industry` 的闭区间**（v1 spec §3.1 的原文形状"0..cycleDays"），**改结算的判据为 `progressed >= cycleDays`** ⇒ 该状态下收获并归零，语义正确（`progressDays == cycleDays` 的含义就是"周期已满、待收获"）。
   不选"收紧上界为 `cycleDays - 1`"的理由：那会与 v1 spec §3.1 的原文冲突，且把"周期已满"这个合法状态变得不可表达。
4. **非 `Split` 的分配函数不许留到日推进才炸** —— `EconomySettlement.java:383-387` 对 `AllocationRule.WageFirst` 直接抛 `UnsupportedOperationException`，异常穿出 `EconomyTimeParticipant.simulateWorld` → `TimeAdvance`。⇒ **在构造期/播种期拒**（`Industry` 或 `EconomyPayloads`），而不是等某天的收获日。
5. **`FlowRow` 必须按周期清零** —— v1 是**只增不减的全时累加器**（`EconomySettlement.java:227-243`），`income/consumed/netSurplus/deaths` 跨周期永久累加，只有 `unmetNeed` 按周期归零。与 v1 spec §3.3「表 3：本期流水（周期结算后归档/清零）」与 §6.5「FlowRow 的任何字段都不出现在 checkpoint 的长期语义里」**直接冲突**。
   ⇒ 后果不只是读数错：**R6 阶层流动的判据"连续三周期赤字"无法从这张表派生**（累计数上第 2 周期起 `netSurplus` 必为正）。
   ⇒ 修法**必须在周期末（按产业）清零，不能在命令边界清零** —— v1 spec §十一 的等价性测试（一次 N 天 == N 次单日）逼出"跨命令累加"是对的，清零粒度要按周期。`deaths` 一并归入本期口径（与其它字段一致），累计量若需要，另存或从历史导出。
   ★ `FlowRow.deaths`（本期死亡人口）在 §1.3 摘掉致死之后**恒为 0**。字段**保留不删**（v1 spec §3.3 的形状，且"判断结果"落地时要用），但必须在字段注释里写明"当前恒 0，因为致死判据未实现"——不许出现"看起来在记、其实永远是 0"的静默字段。
6. **消费取整残差必须分派，不许丢** —— v1 spec §十「取整残差按 id 分派，不丢总量」；实现只算 `population × 83`（`EconomySettlement.java:284`、`EconomySeeder.java:305`）。10 粮/周期 ÷ 120 天 = 83.33 ⇒ 每人每周期实吃 9,960 ≠ 10,000（**−0.4%**，三国全境每周期少约 47.3 万粮）。
   ★ `EconomySettlement.java:280-281` 的注释把这个偏差解释成"整数乘法、无除法残差"——**残差来自 10 粮 ÷ 120 天，不来自除法**，该注释是错的。
   ★ `EconomySeederTest` 现在把"人口 × 83"当正确值断言（`:191/:315`）⇒ 补齐残差必须同步改这些用例。
7. **分配残差按权重摊，不是按人头均摊** —— `distributeResidue`（`:480-496`）把权重和的缺口（真实四行算出的 Σ权重 = 998‰，丢 2‰）**平均分给每一行**。按格净产 5,950,000 毫粮算 ⇒ 11,900 毫粮四行均分（每行 2,975），而地主按权重应得 429 ⇒ **实得是应得的 7 倍**。量级小，但它是**系统性偏向平均**、与"制度分配决定谁得多少"反向，且已被 `EconomySettlementTest:227-233` 钉住。
   ⇒ 改用最大余数法（按权重余数排序分派），与 `EconomySeeder.splitByShares` 的口径统一。
8. **读数必须与结算同源** —— `ClassRow.naturalNeeds` 生成时写一次（`EconomySeeder.java:274`），结算**不读它**（另按 `人口 × 83` 现算），而 GUI 读口把**旧字段**当"日耗"显示（`ApiViews.java:411`，字段名 `grainDailyConsumption`）。人口一旦变化（v1 的饿死、将来的任何人口变动）两者即分叉，**同一面板上 `population` 是新值、"日耗"是旧值**。
   ★ `EconomySettlement.java:280-281` 明文断言"`naturalNeeds` 在 v1 人口不变时恒等于它"——**该断言已为假**。
   ⇒ **一条真相**：要么结算读/写该字段，要么读口改用 `人口 × 口粮系数`。二者取一，并加测试钉住"读口日耗 == 结算当日实吃"。
9. **跨切片守恒** —— 粮食总量 = `economy 各阶层库存 + Σ部队 equipment 里的粮 + 政府库存`。v1 只有切片内守恒（且"钱守恒"因 `money` 恒 0 而是**空判据**）。§五 的索取源落地后守恒变成跨切片，校验点本该住在**尚不存在的 `EconomyDayCoordinator`** ⇒ 本版先建校验点（哪怕只有 economy 一个切片），随 provider 增多而变真。
